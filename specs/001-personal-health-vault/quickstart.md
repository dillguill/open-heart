# Quickstart: Personal Health Vault

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Data model**: [data-model.md](./data-model.md) | **Contracts**: [contracts/](./contracts/)

Validates the feature end-to-end against the spec's user stories and success criteria. Does not
contain implementation code — see `tasks.md` (generated by `/speckit-tasks`) for that.

## Prerequisites

- Node.js 20+, and either `npm` or `pnpm`
- Expo CLI (`npx expo` — no global install needed) and an Expo/EAS account for Dev Client builds
- iOS: Xcode + a simulator, or a physical device with the project's Dev Client installed
- Android: Android Studio + an emulator, or a physical device with the project's Dev Client
  installed
- **Expo Go will not work** for this project — the app depends on native modules (op-sqlite,
  llama.rn, expo-local-authentication) outside Expo Go's fixed module set. Use a Dev Client build.

## Native app: setup

```bash
npm install
npx expo prebuild            # generates native ios/ and android/ projects (CNG)
npx expo run:ios             # or: npx expo run:android
```

## Native app: validation scenarios

Each scenario maps to a spec user story and its acceptance criteria.

### 1. Store data and documents locally (User Story 1 / SC-001)

1. Launch the app, complete the app-lock setup (passcode/biometric).
2. Add a manual Health Record (e.g., a blood pressure reading) — confirm it appears in the
   record list in well under 30 seconds end-to-end (SC-001).
3. Import a sample PDF as a Document — confirm it appears associated with today's date.
4. Force-quit and relaunch the app, unlock, and confirm both persist.
5. Enable Airplane Mode and repeat steps 2–4 — confirm nothing fails (SC-003).

### 2. Trends (User Story 2 / SC-002)

1. Add three Health Records of the same `metricType` (e.g., weight) on three different dates.
2. Open Trends, select that metric — confirm a chronological chart renders in 3 or fewer
   taps/clicks from the home screen (SC-002).
3. View a metric with only one recorded point — confirm it renders without error and indicates
   more data is needed.

### 3. Doctor summary (User Story 3 / SC-004)

1. With records across at least 3 categories present, open the doctor summary view — confirm it
   opens in under 1 minute of intent (SC-004) and groups content by category with trend
   highlights.
2. Export to PDF and use the share sheet — confirm the resulting file opens correctly outside the
   app (e.g., in the Files app / Mail) without requiring an account.

### 4. AI interpretation (User Story 4)

1. With no external AI configured, request an explanation of a stored lab value — confirm the
   local model (if downloaded) responds with a plain-language, clearly labeled non-medical-advice
   explanation, or the app clearly states local AI is unavailable if the model hasn't been
   downloaded yet.
2. Configure an external AI provider — confirm the app shows the data-sent disclosure and
   requires explicit opt-in before the first request (FR-010).
3. Confirm the response is labeled non-medical-advice regardless of source (FR-009).

### 5. Data control (FR-007)

1. Delete a single Health Record — confirm it's gone from the list and no longer appears in
   Trends.
2. Wipe the profile's entire data store — confirm all records/documents are gone and the app
   returns to an empty state without needing external support.

### 6. Multi-profile isolation (FR-015)

1. Create a second (dependent) profile.
2. Add distinct data to each profile — confirm switching profiles requires re-authentication and
   that one profile's data is never visible while the other is active.

## Web demo build (GitHub Pages showcase)

```bash
npx expo export --platform web
# outputs to dist/ — add a .nojekyll file so GitHub Pages doesn't strip the _expo directory
touch dist/.nojekyll
```

Deployment is automated via `.github/workflows/gh-pages.yml` (built in the tasks phase) on pushes
to the default branch; `app.config.ts` sets `baseUrl` to the repository path so asset URLs
resolve correctly under `https://<user>.github.io/<repo>/`.

### Web demo validation

1. Open the deployed GitHub Pages URL — confirm the app loads pre-populated with fixture Health
   Records, Documents, and an AI-explained sample entry, all visibly labeled as demo data.
2. Confirm no network request to any AI provider occurs (check the browser network tab) — all AI
   explanation text in the demo comes from local fixtures.
3. Confirm the app is clearly labeled somewhere in the UI as a demo build not intended for real
   health data.

## Automated checks

- Unit/component: `npm test` (Jest + React Native Testing Library)
- End-to-end flows: `npx maestro test e2e/` — one flow per user story above, run against a Dev
  Client build on a simulator/emulator
